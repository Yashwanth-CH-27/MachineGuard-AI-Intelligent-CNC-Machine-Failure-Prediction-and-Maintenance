# Academic project report

**Title:** MachineGuard AI: Intelligent CNC Machine Failure Prediction and Maintenance

**Classification:** Applied machine learning / predictive maintenance (educational prototype)

**Deployment:** Local Windows application with Streamlit web interface

## Abstract

MachineGuard AI is a decision-support prototype for examining industrial machining operating measurements and predicting whether a record resembles a machine-failure observation. It consumes product quality variant, air and process temperatures, rotational speed, torque, and tool wear. The project includes a leakage-safe supervised learning pipeline, calibrated binary model comparisons, an inspection interface, batch prediction, an interactive dashboard, transparent source provenance, local inspection history and exportable reports. The prepackaged model is trained on locally generated simulated records; when the official publicly available UCI AI4I 2020 dataset can be downloaded, the application can retrain on that **separate synthetic benchmark**. Neither dataset is real live sensor data, so no industrial effectiveness is asserted.

## 1. Introduction

Unexpected faults in machining operations can delay work and require inspection. Measured variables such as thermal conditions, spindle RPM, torque and tool wear can be useful in identifying operating regimes associated with failures. Machine learning allows a statistical classification model to be fitted using labeled historical examples and used to score new inputs. This project evaluates the use of such an approach in a controlled academic environment.

## 2. Problem identification

The core problem is estimating failure risk from a small number of operating parameters, rather than diagnosing one known fault type or computing time to failure. A useful educational application must support manual entry, multiple-row CSV ingestion, explainable model behavior, and honest evaluation against held-out labels. Rare failure examples make plain accuracy a poor standalone metric.

## 3. Existing approaches

Traditional maintenance strategies include scheduled periodic checks, condition-based monitoring and experienced operator judgment. Supervised classification can complement these by learning nonlinear associations between sensor-like measurements and labeled failures. However, insufficient real data, class imbalance, operational variation, spurious correlations and false negatives restrict performance. The AI4I 2020 benchmark is useful for controlled experimentation, but it is **synthetically generated**.

## 4. Proposed methodology

The workflow: collect compatible labeled records → validate raw features and target → review missing/duplicate counts and imbalance → split train/validation/test → engineer physical interaction variables → preprocess and fit models → calibrate scores → compare models on validation average precision → choose validation F1 threshold → evaluate once on test → package trained model → expose local dashboard, single inspection and CSV batch inspection. All input features are available at inference. Outcome labels or IDs are never used as model predictors.

## 5. System architecture

The UI layer consists of the five Streamlit views. The inference layer validates measurement frames, calls the fitted pipeline and adds heuristic inspection priority. The modeling layer trains and evaluates candidate calibrated sklearn pipelines. The storage layer holds a CSV dataset, a joblib model, JSON evaluation results and local history CSV. A Windows BAT file automates virtual environment creation, pip dependencies, data/model bootstrap, and browser startup.

## 6. Dataset description and provenance

There are two explicitly separate sources:

**Packaged offline source:** `machining_simulated.csv` generated by `src/simulation.py`; 10,000 independently simulated records created to represent hypothetical machining conditions. The generator introduces temperature variation, correlated speed/torque, periodically resetting tool wear, illustrative thresholds and random label noise. **It is not an extracted UCI file and cannot be called an external benchmark.**

**Optional official source:** the AI4I 2020 Predictive Maintenance Dataset from the UCI Machine Learning Repository (2020), 10,000 synthetic observations, DOI 10.24432/C5HS5C, CC BY 4.0. It may be downloaded during startup and then supersedes the simulated source. The project does not imply that either source is factory telemetry.

Raw model features: Type (L/M/H), air temperature (K), process temperature (K), rotational speed (rpm), torque (Nm), tool wear (min). Label: machine failure (0/1). Identifiers and failure-mode target columns are excluded. **L/M/H refers to product quality, not CNC machine brand or type.** See [dataset attribution](../data/DATASET_ATTRIBUTION.md).

## 7. Preprocessing

The data loader checks schema, missing values, invalid ranges and target values, and reports duplicate observation counts. Engineered features are temperature difference, estimated spindle power in kW, and wear–torque interaction. Training-fold-only preprocessing applies imputation, numeric scaling and categorical one-hot encoding. All transforms execute within sklearn pipelines and calibration folds to reduce leakage risk.

## 8. Algorithm selection

Three candidates are compared: Logistic Regression (linear reference), Decision Tree (interpretable nonlinear splits), Random Forest (ensemble capable of nonlinear interactions). Models use class weighting for rare failures, and each is calibrated with three-fold sigmoid fitting. Average precision on validation labels is the primary ranking metric because the positive class is infrequent. A decision threshold is chosen by validation F1 and then locked for final test assessment.

## 9. Experiments and evaluation

Actual metrics are saved in `../models/training_results.json` with dataset provenance, training timestamp in model package, comparison results, split sizes and held-out confusion matrix. The document deliberately does **not** hardcode metrics that might become stale after retraining on the official dataset. To reproduce this report, run `python bootstrap.py --force-train` and open **Model Intelligence**. Metrics available: accuracy, precision, recall, F1, ROC-AUC, average precision, Brier score, confusion matrix and validation permutation importance. Accuracy alone is insufficient because most observations have no failure label. Calibration does not establish reliability beyond similar synthetic distributions.

### How to interpret results

Precision is the proportion of flagged records that truly have failure labels. Recall is the proportion of failure labels detected. A false negative is a missed failure. Average precision integrates performance across positive-class precision/recall operating points, making it useful when failure labels are uncommon. Model-selection results are measured on **validation**; only the final selected estimator is measured on the separate **test** partition.

## 10. Interface and functionality

The application provides an overview KPI page, manual measurement form, downloadable HTML inspection report, CSV batch input/output, local history log, confusion matrix, comparison plots and permutation importance. Invalid CSV columns/values produce actionable error messages. Operator review priorities are score-based heuristics rather than a separately trained or professionally validated maintenance schedule. The tool does not predict exact failure modes, real-time next-hour failures, or remaining machine life.

## 11. Testing

Unit and integration tests cover simulation reproducibility, valid/invalid input handling, target leakage prevention, preprocessing, packaged artifact predictions, batch inference, HTML encoding, report metrics and local history. Training was executed and produced numeric metrics with a real fitted scikit-learn model. For platform-specific validation, run `START_PROJECT.bat` on a Windows 10/11 laptop with Python and internet available. The author's Linux-side test environment cannot directly verify BAT execution and must not claim to have done so. See [test results](TEST_RESULTS.md).

## 12. Limitations and ethical considerations

The main limitation is synthetic data. Learned relationships may come from generator rules rather than complex industrial phenomena. A stratified random split also need not represent unseen machines, factories, or future sensor drift. Review priorities depend on heuristic thresholds. False negatives remain possible and should not encourage reduced inspection or unsafe operation. Real deployment would require measured factory data, equipment-specific calibration, qualified industrial experts, regulatory and safety review, and continuous post-deployment monitoring.

## 13. Conclusion

MachineGuard AI demonstrates a complete end-to-end machine learning workflow within a manageable student project: validated data, leakage-safe fitting, multiple algorithms, calibrated risk scores, transparent evaluation, an interactive application, one-click-oriented launching, and detailed documentation. It is designed as an **educational inspection aid**, not certified maintenance software. The provenance-first design prevents confusion between built-in demo simulations and the separately obtainable AI4I synthetic benchmark.

## 14. Future enhancements

Potential extensions after access to real labeled machine data include machine-specific models, anomaly detection from temporal sensor sequences, drift detection, inspection feedback capture, calibrated alert thresholds optimized against real maintenance costs, and sensor integration. None of these extensions is represented as currently implemented.
